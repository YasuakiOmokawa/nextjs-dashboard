# db

- 表の定義は `drizzle/schema.ts`、migration は root の `drizzle/` (生成の手順は `drizzle/CLAUDE.md`)。
- `drizzle/client.ts` の `db` は、Node (テスト) では `DATABASE_URL` の単一の Pool を、Worker では `drizzle/pool.ts` の `runWithRequestPool` が開く要求ごとの Pool を使う。`drizzle/pool.ts` を import できるのは Worker の入口と `client.ts` だけで、`biome.json` の `noRestrictedImports` が止める。入口は `biome-ignore` で 1 行だけ許す。要求ごとの Pool は、入口が渡す `waitUntil` の中で `runWithRequestPool` が閉じる。
- 事業所のデータの表は `company_id` と `companyIsolation(table)` の policy を持つ。`__tests__/rls.test.ts` が付け忘れを落とす (ADR-0005)。
- 読み書きは `scoped.ts` の `companyFilter` で絞る (ADR-0002 D4)。RLS が読む `app.company_id` は `withCompanyScope` が transaction の中だけに設定する。
- 読み取りの関数 (`team_list`・`team_matrix` は migration `0012`、`company_team_list`・`bump_company_team_list` は `0014`) は、先頭の `set_config(..., true)` で、その関数を呼んだ SQL 文の中だけに `app.company_id` を設定し、SECURITY INVOKER で RLS を効かせる。関数の中の絞り込みは `companyFilter` を通らないので `<別名>.company_id = p_company_id` で書く。SQL の中でチームが見える範囲 (管理者か、割り当てられた人) を決めるのは関数 `team_visible_to` だけで、`team_list`・`team_matrix` と `TeamService` の `saveMyLevels` が呼ぶ。`__tests__/team-functions.test.ts` が、この形の絞り込みを `TRUE` にしても RLS だけで他社が見えないことと、設定が次の文に漏れないことを見る。Worker が一覧に呼ぶ関数は `company_team_list` だけで、見える範囲は `src/services/team-reads.ts` の `TeamReads` が同じ規則で絞る。`team_list` は、その規則が `team_visible_to` と食い違うとテストを落とす比べ相手として残す。
- 事業所・チーム・スキルの id は brand で、列の `$type` が付ける。`TeamId`・`SkillId` は SPA も読む `ids.ts` に置く。`CompanyId` は `company-id.ts` に置く。`CompanyId` は taimei-auth の SDK から事業所 id の形を読むので、`ids.ts` に置くと SPA の成果物に SDK が入る。値は Schema で作り、`as` は使わない。`TeamId`・`SkillId` は decode で、`CompanyId` は形を検査する `make` で作る。試験の事業所 id は `src/services/__tests__/db/seed.ts` の `fixtureCompanyId` で作り、事業所 id の形を試験に書かない。テスト以外で `CompanyId` を作るのは、session を確かめる `src/auth.ts` の `requestSessionOf` と、DB の行を読む `purgeDeparted` だけ。作る箇所を足したら、ここに書く。
- test_db と e2e の DB は superuser で接続し、RLS を通らない。policy を観測するテストは、`src/services/__tests__/db/test-db.ts` の `switchToRoleWithoutRlsBypass` で transaction の中で BYPASSRLS の無い role に切り替える。
- DB のテストは `src/services/__tests__/db/test-db.ts` の `withRollback` で 1 テスト 1 transaction。一意制約の違反を見るテストは、書き込みを savepoint (`db.transaction`) に入れないと transaction ごと中断する。`set_config(..., true)` は savepoint を抜けても外側の transaction の終わりまで残る。
- チームの一覧は、事業所ごとの Durable Object (DO) の SQLite に写した表から読む (ADR-0008)。一覧の新しさは `company_team_list_versions` の版で比べる。一覧を変える書き込みは `src/services/company-team-list.ts` の `writeTeamList` を通し、同じ transaction の中で `bump_company_team_list` を呼んで版を増やす (`bump_company_team_list` は版を増やす文と一覧を読む文を分ける。理由は `drizzle/0014_company_team_list.sql`)。版を増やさずに一覧を変えた後 (手作業の SQL) と、DB を backup から戻した後 (版が過去に戻る) は、GitHub Actions の Deploy を流し直す。流し直すまで古い一覧が出る (DO は寿命が切れても、同じ版なら一覧を書き直さない)。
